# Professional Course Audit — 2026-08

This report audits the Systems Engineering Course for pedagogical sequencing, technical correctness, practical usefulness, assessment quality, and sustainable workload.

The audit intentionally treats upstream `project-based-learning` tutorials as **candidate learning assets**, not automatically valid modern course specifications.

---

# 1. Executive verdict

The pre-audit course had a strong direction but was **not yet safe to treat as a self-contained curriculum**.

Its main strengths were:

- project-first philosophy;
- strong low-level/systems scope;
- sensible Russian/English source mix;
- integration of CS fundamentals instead of language syntax only.

Its main weaknesses were:

- hidden prerequisites in several milestone tutorials;
- overloaded modules;
- historical tutorials treated too much like current implementation guides;
- weak guarantees that algorithms/testing/debugging/operability would actually be learned;
- insufficiently concrete assessment criteria.

The audited version corrects these issues and changes the course from a roadmap into an executable syllabus.

---

# 2. Critical vulnerabilities found

## Vulnerability 1 — Hidden prerequisites

Examples:

- Kilo terminal code uses bit masks/bitwise operations before the old course guaranteed they were taught.
- The original Linux debugger series implements the debugger in C++ and later uses `libelfin`, while the course teaches C, not C++.
- The allocator tutorial uses `sbrk()`, which is historical/obsolete as a modern portable teaching backend.
- Linux container labs require Linux-specific namespace/cgroup behavior and sometimes privileges that a generic Windows/macOS path does not provide.

### Fix

Every module now declares prerequisites. Bitwise operations move earlier; debugger core becomes C; allocator uses an arena backed by `mmap`/course-approved buffer; Linux-specific labs use the canonical WSL2/Ubuntu environment with VM/native-Linux fallback where required.

---

## Vulnerability 2 — Cognitive overload and too many large projects

The old Module 6 combined:

- OS scheduling;
- virtual memory;
- synchronization;
- filesystems;
- database internals;
- Linux container;
- FUSE filesystem;
- simple database.

That is multiple university-scale units and multiple portfolio projects in one module.

### Fix

The audited course separates concerns:

- OS/isolation gets its own module;
- filesystem/database internals get their own module;
- Kilo/FUSE become **Guided labs**, not mandatory full portfolio projects;
- only one large core milestone is active at a time whenever practical.

---

## Vulnerability 3 — CS topics could silently disappear

The old wording used phrases such as "algorithms inserted when useful". This makes it possible to finish the systems projects while never systematically reaching graphs, priority queues or dynamic-programming fundamentals.

### Fix

Mandatory CS checkpoints are now assigned to concrete modules:

- Module 0: linear search / first complexity intuition;
- Module 1: Big-O/Θ, search/sort, recursion, BST/heap concepts, DP fundamentals;
- Module 3: number representation, Boolean logic, CPU/assembly;
- Module 5: graphs, BFS/DFS, heap review, Dijkstra;
- Modules 4–9: measurement, queueing, storage/index and architecture reasoning.

Math remains just-in-time, but the required concepts are explicit.

---

## Vulnerability 4 — Historical tutorials were treated as authoritative current specs

Several excellent tutorials are old enough that copying their environment/API choices directly would teach unnecessary legacy behavior.

Examples:

- Brennan shell tutorial (2015): useful baseline, deliberately very limited grammar.
- Kilo: pedagogically excellent, but a full ~1000-line/184-step editor is too large to make mandatory before the shell.
- `Memory Allocators 101`: teaches allocator ideas but uses `sbrk()`.
- `Linux Container in 500 Lines of Code`: valuable historical walkthrough, but old kernel/cgroup assumptions should not define a 2026 core lab.
- historical FUSE tutorial: current course should target libfuse 3 official examples/API.
- Sy Brand Linux debugger (2017): excellent concept series, but C++/libelfin create undeclared prerequisites.
- cstack database tutorial: good page/B-tree progression, but it does not implement a complete transactional/WAL database.

### Fix

Every milestone source gets a role:

- `PRIMARY`
- `REFERENCE`
- `EXERCISES`
- `GUIDED LAB`
- `HISTORICAL REFERENCE`

Current standards/docs override old tutorial implementation details.

---

## Vulnerability 5 — Project completion was underspecified

"Build the project" is not an assessment rubric.

Without explicit criteria a learner may:

- copy tutorial code;
- pass one happy-path demo;
- have memory races/leaks;
- not understand the design;
- still mark a milestone complete.

### Fix

All core modules now require evidence across:

1. explanation;
2. correct implementation;
3. transfer feature;
4. debugging;
5. engineering review.

Projects add tests, failure scenarios, design limitations and measurable criteria where appropriate.

# 4. Audited course architecture

The course now has ten finite core modules:

| Module | Main outcome | Core milestone |
|---|---|---|
| 0. C Fast Start | syntax + fixed representation | MiniKV v0 |
| 1. Memory & Data Structures | pointers/ownership/algorithms | Hash Table |
| 2. Unix & Shell | processes/FDs/pipes | Unix Shell |
| 3. Computer Architecture | CPU/machine code/ABI | VM/Emulator + Nand2Tetris 1–6 |
| 4. Virtual Memory & Performance | cache/pages/allocator | Arena Allocator |
| 5. Networking & Concurrency | TCP/framing/threads/backpressure | Concurrent KV Server |
| 6. OS & Isolation | scheduling/VM/sync/namespaces/cgroup v2 | Mini-container/isolation lab |
| 7. Filesystems & DB Internals | persistence/pages/B-tree | Simple Database |
| 8. Binaries/Debugging/Security | ELF/ptrace/hardening | Minimal Debugger in C |
| 9. Systems Integration & Architecture | observability/failure/capacity | Persistent KV Service capstone |

Expected calendar at 6–8 h/week is roughly **15–20 months including consolidation buffers**, not because every week must be full, but because systems projects are variable and rushing them destroys the learning value.

---

# 5. Cognitive-load policy

The audited course uses these rules:

- normally one teaching source + one reference + one active project;
- theory blocks are 10–45 minutes, not full chapters by default;
- project work starts before theory is "complete";
- one large milestone at a time where practical;
- guided labs can be partial by design;
- every 4–6 weeks / major milestone allows consolidation buffer;
- environment/version friction is escalated quickly instead of consuming an entire study session.

---

# 6. Practical/artifact policy

Every core milestone leaves:

- source code;
- automated or repeatable tests;
- README with supported/unsupported behavior;
- design/ownership notes where relevant;
- one transfer feature;
- one debugging story;
- engineering review;
- incremental Git history.

Performance/network/service milestones additionally require a reproducible workload and metrics.

---

# 7. Interaction and knowledge checks

Questions should test causal understanding, for example:

- Why does keeping one pipe write descriptor open prevent EOF?
- Why can TCP split one application message across reads?
- What fails if a hash table deletes an open-addressed bucket without a tombstone/rehash strategy?
- Why can a process reserve more virtual address space than physical RAM?
- Why can two `O(n)` loops have materially different runtime?
- Why is namespace isolation not equivalent to a complete security boundary?
- What happens to a B-tree operation if a process crashes halfway through a page split?
- Why does ASLR not fix memory corruption?

These replace recall-only questions such as "define a file descriptor" wherever possible.

---

# 8. Technical currency decisions

As of the 2026 audit:

- POSIX API reference should target POSIX.1-2024 / current man pages.
- libfuse course work targets libfuse 3 official examples/API.
- Linux resource control is taught using cgroup v2 terminology/design.
- allocator core does not recommend `sbrk()`; it uses `mmap`/controlled arena.
- debugger core is C + Linux/x86-64 `ptrace`; the C++ tutorial is reference material.
- cstack database is used for REPL/pages/B-tree progression, while WAL/transactions remain a separate conceptual foundation unless implemented explicitly.

---

# 9. Remaining intentional limits

A finite core cannot teach everything.

The following remain advanced branches:

- consensus / replication / sharding;
- kernel-driver development;
- production container runtime/OCI implementation;
- advanced exploit development;
- full DWARF debugger;
- C++ as a language track;
- compilers/runtimes;
- Rust;
- embedded/RTOS.

The final capstone is the gate into distributed systems/architecture because it first requires competent reasoning about a **single-node** system under load/failure.

---

# 10. Audit result

After the changes in this branch, the course is suitable to use as a living curriculum **provided individual lesson assignments are generated from the module specs rather than asking the learner to independently consume whole sources**.

The canonical operational loop is:

```text
module spec
  ↓
assigned exact source section
  ↓
understanding check
  ↓
small exercise/lab
  ↓
project slice
  ↓
rubric/review
  ↓
progress update
```

The repository is therefore both:

- a durable syllabus and progress source of truth;
- a scaffold for instructor-led lessons in chat.
