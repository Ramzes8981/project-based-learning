## Цель

Понять fixed arrays и null-terminated C strings достаточно хорошо, чтобы реализовать линейный поиск без выхода за границы и без неявного сужения индексов.

## Prerequisite check

1. Что означает `sizeof(int)`?
2. Что такое loop invariant своими словами?
3. Почему функция не знает автоматически «намерение» caller насчёт допустимых индексов?

## Инженерный контекст

Python list хранит богатую runtime-структуру: длину, ссылки на элементы, capacity и т.д. Raw C array гораздо ближе к набору однотипных элементов в contiguous memory.

Это даёт контроль и предсказуемость, но снимает часть защитных механизмов.

## Fixed array

```c
int numbers[4] = {10, 20, 30, 40};
```

Массив содержит четыре `int` подряд.

В пределах той же scope можно вычислить число элементов:

```c
size_t count = sizeof(numbers) / sizeof(numbers[0]);
```

Но не превращай это в магическую универсальную формулу для любого parameter: позже увидим, что array parameter в функции имеет особые правила и обычно не сохраняет информацию о длине.

## Границы

Допустимые индексы массива длины `N`:

```text
0 ... N-1
```

Доступ за границей — undefined behavior. Это не обещанный exception.

Поэтому функции, работающие с массивом, обычно получают/знают длину отдельно.

## C string

Стандартная C-строка — последовательность `char`, завершающаяся нулевым байтом `\0`.

```c
char word[] = "cat";
```

Фактически требует места для:

```text
'c' 'a' 't' '\0'
```

Поэтому array size здесь 4, а логическая длина строки — 3.

## `strlen` и `strcmp`

`strlen(s)` идёт по байтам, пока не найдёт `\0`.

Если переданная область не содержит terminator в пределах доступного объекта, `strlen` продолжит чтение за допустимой границей; такое использование приводит к undefined behavior, а не просто к «неправильной длине».

Для сравнения строк по содержимому используют `strcmp`, а не `==`.

```c
if (strcmp(a, b) == 0) {
    /* equal text */
}
```

Оба аргумента `strcmp` тоже должны указывать на валидные null-terminated strings.

Почему `==` не подходит, станет окончательно ясно после pointers; пока зафиксируй: для C strings сравниваем содержимое библиотечной/собственной функцией.

## Safe copying как контракт

Слепое копирование строки без проверки capacity опасно.

Если `len` — число символов **без** terminator, а `capacity` — размер destination buffer в `char`, безопасный критерий размещения обычной C string:

```text
len < capacity
```

Тогда остаётся место для `\0`.

Полезная схема:

```text
1. узнать/проверить source length
2. убедиться, что len < destination capacity
3. скопировать ровно len символов
4. записать terminator в destination[len]
```

Позже разберём конкретные memory/string APIs глубже. Сейчас важен контракт границ.

## Linear search

Для массива:

```text
[12, 8, 5, 19, 3]
```

поиск `19` может проверять элементы по порядку.

В худшем случае придётся проверить `N` элементов. Мы обозначаем верхний порядок роста как `O(n)`.

Пока это **не** полноценная лекция по asymptotic analysis. Достаточно понять проблему роста работы вместе с размером input.

## Индекс и `not found`

Length уже имеет тип `size_t`, поэтому естественно не сужать найденный индекс до `int`.

Один простой контракт для упражнения:

```text
0 <= result < count  -> найденный индекс
result == count      -> not found
```

Почему sentinel `count` безопасен: ни один валидный индекс массива длины `count` не равен `count`.

Это не единственный возможный API. Позже мы увидим status + out-parameter, pointers и Rust `Option`. Сейчас цель — не создавать narrowing cast без необходимости.

## Почему MiniKV начинается с плохого поиска

Мы намеренно строим первую версию так:

```text
GET(key)
   ↓
entry 0?
entry 1?
entry 2?
...
```

При 10 записях это терпимо. При миллионах — уже архитектурная проблема. Именно это позже создаст естественную необходимость hashing.

## Causal questions

1. Почему строке `"abc"` нужно 4 bytes в обычном `char[]`?
2. Почему отсутствие `\0` превращает обычный вызов `strlen` в memory-safety problem?
3. Почему array length должен быть частью API-контракта?
4. Почему `count` можно использовать как sentinel `not found` для индекса?

## Упражнение

Создай массив целых значений и функцию линейного поиска.

Контракт:

```text
input: array, length, target
output: индекс первого совпадения как size_t
        или count, если совпадения нет
```

Требования:

- пустой логический массив;
- target в начале;
- target в конце;
- target отсутствует;
- дубликаты → вернуть первое совпадение.

Затем сделай аналогичное маленькое упражнение для массива C strings и `strcmp`.

### Self-check

- никакого чтения за `length`;
- корректное поведение на `length == 0`;
- отсутствующий элемент даёт ровно `count`;
- нет narrowing cast `size_t -> int` для индекса;
- нет warnings;
- можешь сформулировать worst-case число сравнений порядка `n`.

Разбор: [`04-arrays-strings.solution.md`](04-arrays-strings.solution.md).

Открой [`project/SPEC.md`](project/SPEC.md). Пока реализуй только fixed-capacity storage и линейный поиск.

**Не делай:**

- dynamic allocation;
- pointers как отдельную архитектурную идею;
- resize.

Если для function parameter пишешь `char key[]`, воспринимай это пока как синтаксис передачи последовательности символов; точную связь arrays/pointers разберём в Module 1.

## Типовые ошибки

- `<= length` вместо `< length`;
- сравнение strings через `==`;
- забытый terminator;
- вызов string function на невалидной C string;
- копирование key/value длиннее destination capacity;
- использование `sizeof(parameter)` как длины исходного массива;
- возврат индекса через слишком узкий integer type без явного ограничения input size.
