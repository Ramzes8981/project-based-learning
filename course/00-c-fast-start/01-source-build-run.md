## Цель

После урока ты должен уметь объяснить цепочку

```text
source -> compiler/toolchain -> executable -> process
```

и самостоятельно собрать/запустить маленькую C-программу с предупреждениями компилятора.

## Prerequisite check

1. Чем файл с исходным кодом отличается от уже запущенной программы?
2. Что обычно означает «запустить Python-файл»?
3. Что такое exit code хотя бы интуитивно?

Если ответы неточные — это нормально: урок как раз формализует эти понятия.

## Инженерный контекст

В Python можно привыкнуть к модели «написал `.py` → нажал Run». В systems-задачах этого недостаточно: ошибки могут появиться на разных стадиях — preprocessing, compilation, linking или уже во время выполнения.

Если понимать стадии, сообщения вроде `undefined reference` перестают выглядеть как случайная магия.

## Минимальная программа

```c
#include <stdio.h>

int main(void)
{
    printf("hello, systems\n");
    return 0;
}
```

Сохрани её как `hello.c` и собери:

```bash
cc -std=c17 -Wall -Wextra -Wpedantic -g hello.c -o hello
```

Запусти:

```bash
./hello
```

Посмотри exit code:

```bash
echo $?
```

### Что здесь происходит

`hello.c` — текстовый **source file**.

`cc` — фронт-команда toolchain. За ней может стоять GCC или Clang.

`-std=c17` просит использовать язык C17.

`-Wall -Wextra -Wpedantic` включают полезные диагностики. Warning — не всегда ошибка сборки, но в учебном коде непонятный warning нельзя игнорировать.

`-g` добавляет debug information для будущего debugger.

`-o hello` задаёт имя результирующего executable.

`./hello` просит shell запустить executable из текущего каталога.

## Чуть глубже: стадии сборки

Для простой программы удобно мыслить так:

```text
hello.c
  ↓ preprocessor
расширенный C-текст
  ↓ compiler
assembly
  ↓ assembler
object file
  ↓ linker
executable
```

На первом уроке не нужно запоминать все детали. Важно различать две большие области:

- **build time** — программа ещё создаётся;
- **run time** — executable уже загружен ОС как процесс.

### Preprocessor

Обрабатывает директивы, начинающиеся с `#`, например `#include` и `#define`.

`#include <stdio.h>` не «подключает библиотеку во время запуска». На этой стадии компилятор получает объявления функций и типов, нужные для проверки кода.

### Compiler + assembler

Переводят C в машинно-представимое содержимое object files.

### Linker

Соединяет object files и нужные библиотеки. Если код вызывает функцию, но linker не может найти её реализацию, типичная ошибка выглядит как `undefined reference`.

### Executable и process

Executable — файл на диске. Process — запущенный экземпляр программы с собственным состоянием: адресным пространством, регистрами, открытыми ресурсами и т.д.

Один executable может одновременно породить несколько процессов.

## `main` и exit status

Для обычной hosted C-программы `main` — точка входа на уровне C.

```c
int main(void)
```

означает: функция возвращает `int` и не принимает аргументов программы.

`return 0;` традиционно сообщает окружению об успешном завершении. Ненулевой exit status обычно обозначает ошибку или иной неуспешный результат.

## Warning != runtime error

Добавь временно:

```c
int unused = 42;
```

и не используй переменную. При включённых warnings компилятор должен обратить на это внимание.

Цель не в том, чтобы «выключить ругающийся компилятор», а в том, чтобы понимать диагностику.

## Causal questions

Ответь до упражнения:

1. Почему executable и process нельзя считать одним и тем же объектом?
2. На какой стадии естественнее искать `undefined reference`: compilation или linking?
3. Если программа успешно собралась, доказывает ли это отсутствие runtime bugs?
4. Зачем в учебном проекте держать warnings включёнными постоянно?

## Упражнение

Создай `build_probe.c`.

Требования:

- программа печатает одну строку;
- возвращает `0`;
- сначала добавь неиспользуемую локальную переменную и убедись, что warning виден;
- затем исправь причину warning;
- собери программу с canonical flags;
- запусти и проверь exit code.

### Self-check

- итоговая сборка проходит без непонятных warnings;
- executable действительно создаётся;
- после запуска exit code равен `0`;
- можешь показать, какой файл является source, а какой executable.

Если нужен разбор, открой [`01-source-build-run.solution.md`](01-source-build-run.solution.md) только после своей попытки.

## Что обычно ломается

### `cc: command not found`

Это environment problem. Проверь `ENVIRONMENT.md`, а не пытайся лечить C-код.

### `Permission denied` при `./hello`

Проверь, что запускаешь созданный executable в Linux filesystem и что build действительно завершился.

### `No such file or directory`

Проверь текущий каталог через `pwd`/`ls` и имя output-файла.
